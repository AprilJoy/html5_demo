# AI 评价生成 Demo — 产品文档

> 本文档面向产品/技术负责人与 AI 编程工具评估方，记录「AI 评价生成 Demo」从需求拆解到交付的全过程，并重点沉淀两类经验：
>
> 1. **AI 辅助编程工具的使用策略与提效心得**（如何在真实交付中用 AI 把 4 小时级 Demo 做快、做稳、做可评审）；
> 2. **跨平台、跨语种的 Prompt 设计思路与调优过程**（Google 客观英文 vs 小红书种草中文，以及双语标签、摘要 JSON 的工程化处理）。

---

## 一、任务背景

需求来源：一份《AI 评价生成 Demo》任务书。核心交付一个移动端 H5：

1. 顾客勾选消费感受（1–2 个）→ 选择发布平台（Google / 小红书）；
2. 调用大模型生成对应风格的评价文案（Google = 英文客观评论；小红书 = 中文种草笔记）；
3. 支持二次编辑 → 一键复制并跳转发布平台；
4. 附加题：生成「中文摘要 + 商家回复草稿」，推送到团队群机器人（本任务落地为钉钉）。

评审权重：Demo 演示 50% / 项目文档 30% / 附加题 20%。**API Key 安全与成本控制**是明确加分项。

最终形态：1 个腾讯云 SCF Web 函数（前后端同源，GET 返回页面 + `/generate` + `/notify` 三路由），零 npm 依赖、模块化目录、配置外置。本地预览一条命令：`node server/local.js`。

## 二、AI 辅助编程工具的使用策略与提效心得

### 2.1 核心定位：AI 是副驾，人是架构师

本次全程使用对话式 AI（代码智能体）协作，**效率来自「人定方向、AI 做执行」的分工**，而非把需求一扔了之。几条关键心法：

| 心法                     | 说明                             | 本次实例                                                          |
| ---------------------- | ------------------------------ | ------------------------------------------------------------- |
| **先方案、后代码**            | 让 AI 先产出对比方案与取舍，人拍板后再写，避免返工    | 代理层选型：AI 列出 Vercel / Cloudflare / 腾讯云 SCF / 自有服务器对比表，人选定 SCF  |
| **用对话澄清替代一次写需求**       | 需求模糊时，让 AI 复述理解、给出选项，比硬写 PRD 快 | 「不用 Vercel 还有别的吗」「SCF 收费吗」「和纯前端有什么区别」三轮澄清                     |
| **架构能砍就砍**             | 让 AI 按"简单快速"原则做减法，而不是堆功能       | Vue3+Vite 工程 → 单 HTML + 原生 JS；EdgeOne 托管 → SCF 直接返回页面，CORS 消失 |
| **真 bug 交给 AI 修，人审改动** | AI 改完必须自检 + 截图留证，人 review 关键文件 | 编辑框 `autoGrow` 高度拿 0、钉钉关键词不匹配、JSON 占位符被照抄，均 AI 定位修复           |

### 2.2 分阶段策略

每个阶段都遵循同一套节奏：**人给目标 → AI 出代码/方案 → AI 自测 → 人看关键文件 + 截图 → 反馈下一轮**。

### 2.3 具体提效手法（可直接复用的）

1. **让 AI 做"方案商"而非"打字机"**  
   动手前先问"还有哪些方案""区别是什么""收费吗"，AI 给出的对比表帮你避开 Vercel 国内访问不稳、纯前端 Key 暴露等坑。这一步省下的不是写码时间，是**架构返工时间**。
2. **配置外置，让"现场调整"不重部署**
   - 标签、平台、Prompt 风格全部抽到 `config/` 与环境变量；
   - 钉钉 Webhook、关键词、限流阈值走 `.env`；
   - 收益：评审现场若要"加个平台/改下语气"，改配置即生效，不用动代码、不用重新部署——这是文档评审的加分项。
3. **用浏览器自动化做端到端自测，截图留证**
   - AI 用浏览器工具走完整流程：标签限选 → 双平台生成 → 编辑 → 复制跳转 → 商家后台；
   - 每一步 `eval` 校验（如 Google 版 `无 CJSK 字符 / 无 Emoji`），不符即修；
   - 截图存 `docs/screenshots/`，交付时直接作为验收证据。
4. **用脚本暴力排查，代替人肉猜**  
   钉钉报"关键词不匹配"但用户忘了设了哪个词——AI 写了一个循环，**用同一个 token 逐个探测候选词**，10 秒内定位到关键词是 `notice`。这种"让 AI 跑穷举"的排障方式，比来回问用户快一个数量级。
5. **把"兜底"做成保命符**  
   无 API Key 时本地模板文案 + mock 开关，评审现场网络/模型挂掉也能走完闭环。演示的稳定性往往决定印象分。

### 2.4 本次踩过的坑（已修复，供避坑）

- **设计稿链接需登录**：ardot 链接在浏览器里只返回登录页，AI 无法读取 → 先按文字描述实现，用户补截图后按稿重做（`v2`）。**教训：给 AI 素材时优先发截图/导出文件，别发需登录的链接。**
- **本地常驻进程被回收**：`node local.js &` 后台任务在终端关闭时收 SIGHUP 被杀（zsh 打印 `terminated`）→ 改用 `nohup ... & disown` 或 `pm2`。进程本身无自杀逻辑。
- **自动化测试子串误匹配**：`find text "出餐快"` 会命中"出餐慢" → 改用元素引用或 CSS 选择器。

### 2.5 提效量化（主观估计）

| 环节           | 纯手写估算 | AI 协作实际 | 主要省在             |
| ------------ | ----- | ------- | ---------------- |
| 需求拆解 + 技术方案  | 2–3h  | 0.5h    | 对比选型、文档结构        |
| 前端 + 后端首版    | 6–8h  | ~2h     | 样板代码、路由、配置       |
| 设计稿对齐重做      | 3–4h  | ~1h     | 改 CSS/HTML 比从零写快 |
| 钉钉接入 + 关键词调试 | 1–2h  | ~0.5h   | 脚本探测关键词          |
| 端到端自测        | 2h    | 0.5h    | 浏览器自动化批量走查       |

> 注：以上为同一工程师的主观估计，量级意义大于绝对值。真正的收益不在单点省时，而在**多轮迭代的总成本被压低**——本任务经历 7+ 轮需求/设计/后端变更，每轮重做成本都极低。

## 三、API Key 的安全与用量成本处理（加分考察点）

这是任务书明确写的加分项。本方案把"不暴露 Key、不被刷爆、成本可控"做成三层结构，并在**运行日志里实时打印**安全 posture 与每次调用成本，把加分项从"嘴上说"变成"有数据可查"。

### 3.1 三层隔离：Key 永不下前端

```
浏览器(前端)  ──只调──▶  /generate（同源 SCF 函数）
                                  │
                                  ├─ Key 存此处：SCF 环境变量 / 本地 .env（gitignore）
                                  │   （前端永远拿不到，抓包也看不到）
                                  └─ 函数代发 DeepSeek API，返回纯文案
```

| 层 | 做法 | 防什么 |
|---|---|---|
| 前端 | 只调同源 `/generate`，不直接持有 Key | 抓包/源码泄露 Key |
| 服务端 | Key 存环境变量（SCF 控制台 / `.env`），不写进 `config/`（静态资源会发到浏览器） | 源码与静态资源泄露 |
| 部署 | `.gitignore` 拦 `.env`；SCF 打包前排除 `.env`，只走控制台环境变量 | 误提交、误上传 |

> 关键红线：`config/app.config.js`、`config/prompts.js` 是作为静态资源原样发给浏览器的——Key **绝不能**写进这两个文件。

### 3.2 限流防刷

`/generate` 入口按 IP 做内存限流（`RATE_LIMIT_PER_HOUR`，默认 10 次/IP/小时）。演示链接若被公开转发，陌生人狂点也不会把你的 DeepSeek 额度烧穿。启动日志会打印当前阈值：
```
[安全] 限流护栏: 10 次/IP/小时 · 防演示链接被刷爆额度
```

### 3.3 成本护栏

- **模型选型**：用 DeepSeek（`deepseek-chat`），单价约为 GPT-4 的 1/50，Demo 全程预估 < ¥1；
- **输出长度护栏**：`max_tokens=400`，防止模型输出超长文案白白烧 token；
- **质量重试有上限**：函数侧校验不达标最多重试 1 次，避免无限重试刷额度；
- **兜底不烧钱**：无 Key 或模型异常时走本地模板，不再调用 API。

### 3.4 用量可视化（运行日志实时打印）

每次 `/generate` 成功，服务端打印累计用量、近似成本与本次调用耗时：
```
[usage] calls=12 promptTokens=860 completionTokens=240 estCost=¥0.0013 mock=false cost=1820ms
```
`/notify` 同样打印耗时（`cost=..ms`）；EdgeOne 边缘函数则在 `finally` 中打印 `[edge:generate] cost=..ms` / `[edge:notify] cost=..ms`，保证 mock、限流、报错等任意分支都留下耗时记录。启动日志同时打印计价口径，评审方可当场核对"成本确实可控"。计价按 deepseek-chat 估算（输入 ¥1/百万 token、输出 ¥2/百万 token），真实账单以 DeepSeek 控制台为准。

### 3.5 实测成本（本任务）

本任务开发期累计真实调用约 **十数次**，实测成本 **远低于 ¥0.1**（DeepSeek 控制台可见）。SCF 本身在免费额度内（100 万次/月调用），Demo 期账单为 **0 元**。

## 五、跨平台、跨语种的 Prompt 设计思路与调优

### 3.1 设计原则：固定 System + 平台风格配置块

核心结构（生效版本落于服务端 `server/prompts.js`，EdgeOne 边缘函数 `functions/*.js` 各自带一份；前端 `config/prompts.js` 仅保留 `MOCK_TEMPLATES` 兜底模板，不含真实 Prompt）：

```
┌─ System（固定，定义角色与通用约束）─────┐
│ "你是餐饮品牌的评价文案助手。只输出文案  │
│  本身，不要解释、不要前缀。"            │
└───────────────────────────────────────┘
            + 平台风格块（按 platform 注入）
   Google  : 语言=英文 │ 语气=客观 │ 约束=无 emoji/无话题标签/第一人称真实体验
   小红书  : 语言=中文 │ 语气=种草 │ 约束=3~6 emoji/分段呼吸感/带 #话题标签
```

**关键决策：平台 = 风格配置 + 语言 + 输出约束。** 新增平台只加一块配置，不改代码——这是可扩展性的核心，也让 Prompt 调优变成"调配置"而非"改逻辑"。

### 3.2 双平台差异（已实测）

| 维度    | Google（英文客观） | 小红书（中文种草）     |
| ----- | ------------ | ------------- |
| 语言    | 英文           | 中文            |
| 语气    | 客观、克制、像真实食客  | 热情、第一人称、带情绪   |
| Emoji | 0 个          | 3–6 个（数量受控）   |
| 结构    | 段落陈述         | 短句分段 + 呼吸感    |
| 话题标签  | 无            | 末尾 `#品牌 #品类`  |
| 自检规则  | 不含 CJK 字符    | 含 3–6 个 Emoji |

### 3.3 跨语种处理（最易翻车处）

双语场景两个真实坑，均已修复：

1. **标签串味（mock 兜底期）**：底层感受标签（如"出餐快"）在兜底模板里被直接塞进英文文案，导致 Google 版出现中文。  
   → 修复：标签配置加 `labelEn`（英文映射），英文平台走 `labelEn`，中文平台走 `label`。**文案语言与标签语言解耦**。
2. **JSON 摘要被"照抄"**：附加题的摘要/回复草稿要求 JSON 输出，短文本时模型会把 Prompt 里的字段说明（如 `30字以内`）原样写进 `summary`。  
   → 修复：Prompt 改为纯字段说明式 + 显式"只输出 JSON，禁止照抄说明文字"，结构更稳定。

### 3.4 调优过程（从能用到稳用）

调优不是一次写对，而是加"护栏"让输出稳定达标：

```
初版 Prompt ──▶ 发现风格漂移 ──▶ 加输出约束（emoji 数/语言/字数）
     │                                     │
     └──▶ 发现偶发劣质输出 ──▶ 函数侧质量自检 + 失败重试一次
     │                                     │
     └──▶ 发现双语串味 ──▶ 标签 labelEn 映射
     │                                     │
     └──▶ 发现 JSON 被照抄 ──▶ 字段说明式 Prompt + 禁抄指令
```

**质量自检（函数侧，非 Prompt 侧）**&#x662F;稳定器：

- Google 版校验"无 CJK + 无 Emoji"；
- 小红书版校验"Emoji 数量 3–6 + 字数区间"；
- 不达标自动**重试一次**（避免无脑多刷额度），仍不达标才回落兜底文案。

### 3.5 现场可调：Prompt 也走环境变量

为应对评审"现场改 Prompt"环节，`/generate` 的 Google / 小红书风格块支持从环境变量 `PROMPT_STYLE_GOOGLE` / `PROMPT_STYLE_XHS` 覆盖，**改完即时生效、不需重新部署**。这条设计把"Prompt 工程能力"从隐藏项变成可演示项。

### 3.6 实测效果对比（节选真实输出）

- **Google（纯英文，无 emoji）**：
  > "Finally tried Sunny Tea House. The drinks are solid — balanced sweetness, chewy pearls, and the seating area is comfortable enough to linger. Service was quick too."
- **小红书（中文 + emoji + 话题）**：
  > "终于来打卡这家 Sunny Tea House 了！☀️🧋✨ 出餐速度真的惊到我，点完单还没刷完手机就叫我取了～环境也亮亮堂堂的，随手拍都好看📸 #SunnyTeaHouse #奶茶推荐"

## 七、给团队引入 AI 编程工具的建议

1. **把 AI 当"方案商 + 执行者"，不当"许愿机"**：动手前先让它给对比方案和取舍，人定方向，返工最少。
2. **架构决策权留在人手里**：AI 倾向"加一层/引个框架"，人要根据"简单快速"原则做减法——本任务砍掉 Vue/Vite/独立托管，复杂度降一截。
3. **配置与密钥外置**：标签、Prompt、Webhook、限流全外置，现场调整不重部署，也是安全加分项。
4. **让 AI 自测 + 截图**：端到端自动化走查比人肉点快且可复现，截图即验收证据。
5. **Prompt 工程要"加护栏"**：风格约束写进 Prompt，质量校验放在函数侧重试——双保险比单靠 Prompt 稳得多。
6. **双语/多平台场景，语言与内容解耦**：标签、文案、摘要分别处理语言映射，避免串味。
